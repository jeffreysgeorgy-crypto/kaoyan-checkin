## 二、逐字稿

### 开场（0:00 – 0:40）

各位评委老师好，我是（姓名 / 团队名）。我的项目是《基于 openJiuwen 的个人学习规划 Agent》。

一句话概括：这是一个会**记住你学过什么、哪里弱、为什么没坚持下来**的学习规划 Agent。它像一位私人助教，根据你的学习记忆生成计划；当你连续几天没完成时，自动判断原因、调整计划，而且每一步都告诉你「为什么这么调」。

目标用户是备考 2027 年考研的同学。我以一个具体的人举例：大三 AI 专业学生，目标数学一加 408 计算机专业基础综合，每天可用 6 小时。

为什么要做它？市面上大多数学习 App 只会记录打卡，不会「理解」你，更不会「调整」。我们要做的，是让「规划」这件事本身**可记忆、可推理、可解释**。

### 答题点 ①：用户画像与学习记忆如何存储与更新（0:40 – 1:40）

第一个答题点。我把记忆分成四块，全部落在 `memory.json` 里：

- **用户画像**：目标、考试日期、每天可用时长、偏好学习时段；
- **当前计划**：各科目任务及计划时长；
- **学习记忆**：每个科目一条「掌握度、连续未完成天数、近 7 天完成率、弱知识点、反思原文」；
- **规则与重规划日志**：触发阈值、历次调整记录。

关键在「更新」。每天打卡后，系统把一条记录写回记忆，然后实时重算三样东西：**连续未完成天数、近 7 天完成率、掌握度**。掌握度不是拍脑袋，是按公式算的——完成率占 40%、正确率占 40%、学习效率占 20%。这样记忆就随着打卡一天天「活」起来。

还要强调一点：我们存的**不只是数字，还有用户自己的反思原文**，这是后面归因和可解释性的原始材料。

### 答题点 ②：两个 Skill（1:40 – 2:40）

第二个答题点，系统里有两个 Skill，一个诊断、一个重规划。

**第一个 `diagnose`（学习诊断）**。输入是学习记忆，输出是一份诊断报告：整体健不健康、哪些科目预警、严重度多高、原因是什么、主因是什么，还会引用用户的反思原文。调用条件是：生成新计划之前，或某科连续 3 天未完成触发重规划之前。

**第二个 `replan`（动态重规划）**。输入是当前计划加诊断结果，输出是新计划加逐条调整明细——每条都带「调整前、调整后、理由、依据」。调用条件是诊断出预警科目之后。

这两个 Skill 都是**纯确定性的规则，不依赖大模型**。好处是每一步都可复现、可审计、可单元测试。大模型在哪里发挥作用，我放到答题点 ⑤ 讲。

### 答题点 ③④：现场演示 + 动态调整 + 前后对比（2:40 – 4:10）

第三个和第四个答题点我合在一起，用一段演示来讲，因为「动态调整」和「前后对比」是连在一起的。

【操作：运行 `py demo.py`，从开头往下滚动，边滚边讲】

大家看这个演示。第一天，系统先打印一份**用户画像小报告**：各科近 7 天完成率、最薄弱的科目（数据结构，掌握度只有 0.5）、还有用户最近的反思原文。基于这份画像，生成了初始计划，**每一条任务都带一句「安排理由」**——比如数学高优先级放在晚上七点、数据结构掌握度最低所以集中攻坚、英语轻量任务放早晨走艾宾浩斯复习。

然后逐日打卡。数据结构连续三天没完成。到第三天，系统触发了阈值——**连续 3 天未完成**。它先调用 `diagnose` 诊断：严重度高，主因是「方法不当，看得懂但写不出」。再调用 `replan` 重规划：把原来 1.5 小时的「单链表的插入与删除」，拆成「看 30 分钟讲解视频 + 做两道基础题」，时长降到 1 小时。

这就是**计划生成前后的对比**：调整前是一整块 1.5 小时的硬任务，调整后是拆开的、门槛更低的小任务。每一条调整都结构化列出依据——**连续失败多少天、完成率多少、反思原文是什么、结论是什么**。

如果还没完成呢？系统不会一直用同一招。第五天连续失败 5 天，它**升级策略**：把内容降级成「概念梳理 + 错题回顾」；第六天，重规划已两次以上仍未改善，触发**兜底**：换任务类型，并且不再武断下结论，而是给出**三个方向交给用户选**——A 换路径补上指针/链表基础（推荐）、B 降目标把进度顺延到寒假、C 审视考研目标本身。这个逐级加重的「多级兜底链」，是我认为最能体现「动态」的地方。

### 答题点 ⑤：openJiuwen 的作用（4:10 – 4:50）

第五个答题点，openJiuwen 到底承担了什么。我用一句话定位：**openJiuwen 是「决策编排层」**。具体做了三件事：

1. 用 `AgentCard` 描述这个 Agent 的身份和输入输出契约；
2. 用 `@tool` 装饰器，把我的两个 Skill 包装成工具，注册到它的能力管理器里；
3. 跑起一个 **ReAct 循环**——思考、调用 `diagnose`、观察结果、再调用 `replan`、观察，最后由大模型写出一份带理由、带证据的决策日志。

也就是说：**规则负责「算对」，openJiuwen 负责「编排和表达」**。刚才 Day 3 屏幕上那段决策日志，就是 openJiuwen 驱动 DeepSeek V4 现场生成的。

（如果被追问为什么用框架）框架帮我们管好了工具调度、循环终止、会话管理这些工程细节，我们只专注写 Skill 和规则。

### 答题点 ⑥：个性化与可解释性（4:50 – 5:50）

最后一个答题点。

**个性化**在两个层面：一是画像层面——同样是「连续 3 天没完成」，因为用户的反思原文不同，诊断出的主因就不同：写「时间不够」就归因为时间投入不足，写「方法不对」就归因为方法不当，调整策略也跟着变。二是记忆层面——掌握度、完成率这些数字，都是「这个人」自己的历史算出来的，不是通用模板。

**可解释性**是我整个设计最看重的一条。每一条调整都带四样东西：连续失败多少天、完成率多少、反思原文是什么、结论是什么。评委可以顺着这条链一直追到原始数据。我们刻意**不用黑盒**——大模型只负责「把已经算对的结果讲清楚」，不允许它「编结果」。所以这个系统是可审计的。

### 总结 + 展望（5:50 – 7:00）

总结一下：这是一个「**记忆 + 规则 + 编排**」三层结构的学习规划 Agent。六个答题点分别是——① 四块记忆的存储与打卡回写更新；② 两个确定性 Skill；③ 连续三天未完成的动态调整；④ 调整前后对比；⑤ openJiuwen 作为 ReAct 决策编排层；⑥ 个性化归因与全程可解释。

关于落地：它完全可以接进真实的考研打卡系统，把 `memory.json` 换成数据库、把打卡回写换成真实接口，就能变成真实产品——这也是我们下一步要做的事。

我的汇报到这里，谢谢各位评委老师，欢迎提问。

## 三、现场演示操作提示

1. **提前准备**：确认 `.env` 里 DeepSeek V4 的 `API_KEY` 已填好；提前 `py demo.py` 跑一遍预热，保证现场 LLM 调用顺畅。
2. **LLM 兜底**：如果现场网络不好、Day 3 的 LLM 日志没生成，demo 会自动降级为「确定性规则输出」，整条链路照常演示，不影响讲 ③④⑤⑥——这是特意设计的容错。
3. **滚动节奏**：小报告 → 初始计划（安排理由）→ Day 3 调整对比 → Day 5/6 兜底链，这四个画面是重点，放慢；其余快速带过。
4. **建议把控制台字号调大**，让评委看清 `[调整前]` / `[调整后]` 和结构化「依据」。
