# 评委问答 Q&A（标准答案）

> 四个高频追问的参考答法。每个回答都按「结论 → 依据 → 举例」组织，方便现场即兴展开。

## Q1：为什么只处理「连续 3 天未完成」？是不是太死板了？

**结论：不是「只」处理这一种情况，3 天只是第一条触发线；系统是「多级触发 + 逐级加重」。**

完整链条（demo 里逐天演示过）：

| 连续失败天数 | 系统动作 |
| --- | --- |
| 1 天 | 只记录，不打扰（给正常波动留空间） |
| 2 天 | 中等预警，标红提醒，**不改计划内容** |
| 3 天 | 达到阈值，触发 `diagnose → replan`：减少时长 + 拆分任务 |
| 5 天 | 连续失败 ≥ 5 天：降级内容难度 |
| ≥2 次重规划仍未改善 | 换任务类型 + 给出三个方向（推荐 A） |

为什么阈值定 3 而不是 1：

1. **避免过度反应**：生病、临时有事导致的偶发失败不该触发重规划，否则计划天天变，反而不可信；
2. **统计信号足够强**：连续 3 天未完成，基本可以排除偶然性，说明是「方法 / 难度 / 目标」层面的系统性问题；
3. **可配置**：阈值存在 `memory.json` 的 `rules.trigger_replan` 里，不同用户、不同科目都能调。

补充一点：触发条件其实有**两条线，是「或」的关系**——除了「连续失败天数 ≥ 3」，还有「近 7 天完成率 < 50%」。所以不是只盯着「3 天」一个数字。

## Q2：openJiuwen 承担了什么作用？

**结论：openJiuwen 是「决策编排层」——规则负责「算对」，框架负责「编排和表达」。**

具体三件事：

1. **契约**：用 `AgentCard` 声明 Agent 的身份、输入（query）和输出（decision_log）；
2. **工具化**：用 `@tool` 装饰器把 6 个 Skill（diagnose / replan / allocate / interpret_feedback / proactive_scan / reschedule_for_calendar_change）包装成工具，注册到能力管理器；
3. **编排**：跑起 ReAct 循环——思考 → 按需调用 Skill → 观察 → … → 由大模型生成带理由、带证据的决策日志。

为什么不用纯 `if-else` 而要上框架：工具调度、循环终止、会话/记忆管理这些工程细节框架都管好了；未来要继续扩展（比如「生成周报」「调整作息」）或拆成多 Agent 协作，框架的扩展成本更低。

**最关键的设计原则**：大模型只「讲结果」，不「算结果」。决策数据由 `skills.py` 的确定性规则算好，LLM 只负责把它表达成可读的决策日志——这从根上避免了幻觉，保证了可审计。

## Q3：如果重规划多次还是没完成怎么办？

**结论：系统有「多级兜底链」，不会无限重规划同一招；最后一步是「把人请回来」。**

链条（即 demo 的 Day 3 → Day 5 → Day 6）：

1. 第 1 次：**拆分 + 减时长**（降低启动门槛）；
2. 第 2 次：**降级难度**（改概念梳理 + 错题回顾）；
3. 第 3 次（已重规划 ≥ 2 次仍未改善）：**换任务类型 + 给出三个方向（推荐 A）**。

最后一步是关键。当多次自动调整都无效，系统不再武断替用户下结论，而是给出**三个方向交给用户选**：A 换路径——补上指针/链表基础再回到原计划（推荐）；B 降目标——降低近期目标难度、把进度顺延到寒假；C 审视目标——结合时间投入重新审视考研目标本身。系统推荐 A，因为它是代价最小、不牺牲整体进度的选择。这是负责任 AI 的边界：能自动化的自动化，需要用户拍板的交给人来决策。

工程上还有一道保险：`rules.escalation.replan_count_threshold` 可配置，超过就停止自动调整、进入人工确认，避免「自动重规划死循环」。

## Q4：这个系统如何扩展成真实产品？

**结论：架构已经按「感知 / 记忆 / 决策」三层解耦，替换每一层的实现即可，不用推翻重来。**

逐层落地：

1. **感知层**：现有的考研打卡系统（HTML，`localStorage` 持久化）本身就是真实前端，把它当感知层，通过 API 把打卡结果实时回写给 Agent；
2. **记忆层**：把 `memory.json` 换成数据库（SQLite / PostgreSQL + 时间序列表），支持多用户、历史回溯、并发写；
3. **决策层**：openJiuwen 原生支持多 Skill、多 Agent、会话管理，直接新增 Skill（周报生成、作息调整、知识点推荐）或拆成多 Agent 协作；
4. **个性化升级**：接入更多信号（专注时长、错题画像、遗忘曲线），掌握度公式可升级为时序模型；
5. **工程化**：定时触发（每天打卡后自动跑 diagnose）、推送通知、Web / 小程序界面、评测与回归测试。

一句话总结：**演示里它是「离线脚本 + JSON」，但三层边界清晰，每一层都能无缝换成生产级实现**——这正是当初按「感知 / 记忆 / 决策」分层设计的用意。

## Q5：如何验证 demo 输出稳定？

**结论：跑两次 `py demo.py`，对比两次输出即可；确定性部分逐字一致，LLM 部分核心信号一致。**

具体分两层看：

1. **确定性部分（skills.py 规则引擎）**：诊断、重规划、时长分配、阈值触发等全部由规则算出，
   两次运行结果逐字一致，可放心复现。
2. **LLM 部分（决策日志）**：措辞可能因大模型输出而略有差异，也可能因 API 超时/未配置 key
   走「关键词匹配」降级路径，但**核心信号（调整了什么 / 为什么 / 依据）完全一致**。

我们已把降级路径做成一等公民：`LLM 不可用时自动走关键词匹配`，保证任何环境（离线 / 无 key / 超时）
都能跑出完整流程——这正是「可复现、可答辩」的前提。
